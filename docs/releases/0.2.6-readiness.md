# 0.2.6 Readiness Gate

Publishing 0.2.6 to PyPI is the rebuild's first irreversible cutover. This
document decides, from evidence, whether it is safe. It is the readiness-gate
step that ROADMAP §5 "Promotion path and cutovers" requires before that
cutover (Phase 1 Step 3; parent 1.1). Step 4 executes the decision recorded
in §10 and appends its release record here.

- **Gate date:** 2026-10-05
- **Candidate:** `legacy/0.2.x` at `684b516f0a870c83c4dc911c4381c76022cc1cdb`,
  tagged `v0.2.6.dev1` and published to TestPyPI by release run
  [37248670219](https://github.com/nathanramoscfa/pyeconomics/actions/runs/37248670219).
- **Baseline:** `pyeconomics 0.2.5` on PyPI (the latest release).
- **Method:** every item below was run on the gate date. Each records the
  command, the observed result and PASS or FAIL. Old releases were read from
  their archives with `curl`, `tar` and Python's `zipfile`; none was
  installed or executed. Working files lived in a scratchpad outside the
  repository.

Installs used `uv … --no-config` or `pip --isolated`. The operator's
user-level uv configuration adds a package-firewall index ahead of the one
named on the command line, and without `--no-config` uv resolved
`pyeconomics` there instead of on TestPyPI.

**Reachability.** No module under `pyeconomics/` on `legacy/0.2.x` imports
jupyterlab, pytest, setuptools, `pkg_resources` or `distutils` (checked with
`git show` on every `.py` file). pytest is imported only by `tests/`, and
setuptools only by `setup.py`.

- **jupyterlab:** all 14 IDs are in the JupyterLab server or front end:
  XSS in Markdown and the image viewer, the extension manager, settings
  import, language packs, and the extension template. pyeconomics never
  starts or imports JupyterLab, so it does not reach this code. The pin
  holds any environment that installs pyeconomics on 4.1.x. A user who runs
  `jupyter lab` there is exposed whether or not they use pyeconomics.
- **pytest:** a local denial of service through `/tmp/pytest-of-{user}` on
  Unix, only while pytest runs. The package does not reach it.
- **setuptools:** path traversal and remote code execution in the
  `package_index` download functions, and `MANIFEST.in` handling during an
  sdist build. The package does not import setuptools. The 0.2.6 artifacts
  were built by setuptools 84.0.0 in `uv build`'s isolated environment, not
  by 68.2.2 (§2.6). Because the pin is a runtime requirement, installing
  pyeconomics **downgrades** an environment's setuptools to 68.2.2: the
  legacy CI log shows `Successfully uninstalled setuptools-79.0.1`. That
  environment is then exposed whenever something else in it uses
  `package_index` or builds an sdist.

None of this is new in 0.2.6. 0.2.5 has the same pins and the same
exposure, and the pins are part of the artifact that §2 found otherwise
unchanged.

**Options for the maintainer:**

- **Ship the pins unchanged (recommended).** List the advisories as known
  issues in the 0.2.6 release notes, with the setuptools downgrade named,
  and advise users who run JupyterLab or build packages in the same
  environment to install pyeconomics in its own venv. 0.2.x takes security
  fixes only and ends at 1.0.0. Widening jupyterlab to 4.5 and setuptools
  across fifteen major versions is a compatibility change to a frozen
  branch, and it would delay the credential fix.
- **Widen named pins.** This changes `requirements.txt`, so it needs a new
  rehearsal (`0.2.6.dev2`) and this gate run again before a GO is possible.

## 9. Advisory draft

Created with `gh api -X POST repos/nathanramoscfa/pyeconomics/security-advisories --input advisory.json`.
Confirmed with `gh api 'repos/nathanramoscfa/pyeconomics/security-advisories?state=draft'`:

- **GHSA id:** `GHSA-j6rp-vwwv-jrr8` (state `draft`, `published_at` null):
  <https://github.com/nathanramoscfa/pyeconomics/security/advisories/GHSA-j6rp-vwwv-jrr8>
- **Summary:** "pyeconomics 0.2.0-0.2.5 write the FRED API key to the log at
  DEBUG level"
- **Description:** sections for impact, the affected configuration (DEBUG
  logging enabled on the root logger or a handler that receives its records;
  Python's default WARNING level writes nothing), affected versions, the
  patched version 0.2.6, the workaround (keep the root logger above DEBUG),
  key-rotation advice with the FRED URL and deletion of the logs, and 0.2.x
  end-of-life at 1.0.0.
- **Vulnerability:** ecosystem `pip`, package `pyeconomics`, range
  `>= 0.2.0, <= 0.2.5`, patched `0.2.6`. GitHub dropped the
  `vulnerable_functions` entry (`FredClient.__new__`) from the stored
  record, so the description names the class instead.
- **CWE:** `CWE-532` (Insertion of Sensitive Information into Log File).
- **CVSS 3.1:** `CVSS:3.1/AV:L/AC:H/PR:L/UI:N/S:U/C:L/I:N/A:N`, base score
  **2.5 (Low)**.

**CVSS justification:**

- **AV:L.** The key is exposed only in log output written on the user's
  machine or in their CI. An attacker must read those logs; nothing is sent
  over the network.
- **AC:H.** Exploitation depends on conditions outside the attacker's
  control: the victim enabled DEBUG on the root logger and kept or shared
  the output.
- **PR:L.** The attacker needs ordinary read access to where the logs live.
- **UI:N.** No victim action is needed once the logs exist.
- **S:U.** The scope is unchanged.
- **C:L.** A FRED key is a free credential for public, read-only data.
  Misuse spends the owner's rate limit and could get the key suspended.
  It discloses nothing else.
- **I:N and A:N.** The FRED API is read-only. Suspension of an abused key
